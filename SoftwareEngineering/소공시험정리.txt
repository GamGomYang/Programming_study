
### 1. **소프트웨어 프로세스 정의 (Software Process Definition)**
- **소프트웨어 생명 주기(Software Lifecycle)**: 소프트웨어 개발과 유지보수에 필요한 활동을 단계별로 나눈 것.
- **소프트웨어 프로세스**: 소프트웨어 시스템을 개발하는 데 필요한 구조화된 활동 세트.
  - 주요 활동: 
    - **명세(Specification)**: 시스템이 무엇을 해야 하는지 정의.
    - **설계 및 구현(Design and Implementation)**: 시스템 구조를 정의하고 구현.
    - **검증(Validation)**: 고객이 원하는 대로 작동하는지 확인.
    - **진화(Evolution)**: 변화하는 요구에 맞게 시스템을 변경.

#### 소프트웨어 프로세스의 특징
- **예측 가능성(Predictability)**: 프로세스 결과를 예측할 수 있어야 함.
- **결함 제거(Remove Error)**: 프로세스에서 발생하는 결함을 최소화.
- **테스트와 유지보수의 용이성(Testing and Maintainability)**: 시스템 유지보수가 용이해야 함.
- **변경 지원(Supporting Change)**: 변화하는 요구 사항을 반영할 수 있어야 함.

### 2. **소프트웨어 프로세스 모델 (Software Process Models)**
#### 폭포수 모델(Waterfall Model)
- 개발 과정을 **요구 사항 분석 → 시스템 및 소프트웨어 설계 → 구현 및 단위 테스트 → 통합 및 시스템 테스트 → 운영 및 유지보수**의 단계로 구분.
- **장점**: 계획 기반 모델로, 큰 시스템을 여러 사이트에서 개발하는 프로젝트에 적합.
- **단점**: 단계가 끝나야만 다음 단계로 넘어갈 수 있어, 요구 사항 변경에 대한 유연성이 부족.

#### 점진적 개발(Incremental Development)
- **장점**:
  - 변경 사항에 대한 비용이 낮아짐.
  - 고객의 피드백을 신속하게 받을 수 있음.
  - 빠른 기능 배포 가능.
- **단점**: 시스템 구조가 점진적 변경에 의해 저하될 수 있음. 관리자는 개발 상태를 측정하기 위해 정기적인 산출물이 필요함.

#### 통합 및 구성 모델(Integration and Configuration)
- **재사용 지향 소프트웨어 엔지니어링**: 기존 구성 요소를 통합하여 시스템을 구축.
  - COTS(상용 오프 더 셀프) 시스템을 구성.
  - 웹 서비스와 같은 재사용 가능한 구성 요소로 시스템을 통합.
- **장점**: 개발 시간과 비용 절감, 시스템의 빠른 배포.
- **단점**: 시스템이 실제 사용자 요구를 완전히 충족하지 못할 가능성, 재사용 요소의 진화에 대한 통제력 상실.

### 3. **프로세스 활동 (Process Activities)**
#### 소프트웨어 명세(Software Specification)
- **요구 사항 공학 프로세스**:
  - **요구 사항 도출 및 분석**: 시스템 이해관계자가 기대하는 것을 정의.
  - **요구 사항 명세**: 요구 사항을 세부적으로 정의.
  - **요구 사항 검증**: 요구 사항의 유효성을 확인.

#### 소프트웨어 설계 및 구현(Software Design and Implementation)
- **소프트웨어 설계**: 시스템 구조를 정의하고 설계된 구조를 구현.
  - **설계 활동**:
    - **아키텍처 설계(Architectural Design)**: 시스템의 주요 구성 요소와 관계 정의.
    - **데이터베이스 설계(Database Design)**: 데이터 구조 및 데이터베이스 내 표현 방법 정의.
    - **인터페이스 설계(Interface Design)**: 시스템 간 인터페이스 정의.
    - **구성 요소 선택 및 설계(Component Selection and Design)**: 재사용 가능한 구성 요소를 선택하거나 직접 설계.
  
#### 소프트웨어 검증(Software Validation)
- **검증 및 확인(Verification and Validation, V&V)**: 시스템이 명세에 부합하고 고객의 요구를 충족하는지 확인.
  - **단위 테스트(Component Testing)**: 개별 구성 요소 테스트.
  - **시스템 테스트(System Testing)**: 시스템 전체를 테스트.
  - **고객 테스트(Customer Testing)**: 실제 고객 데이터를 사용하여 테스트.

#### 소프트웨어 진화(Software Evolution)
- 소프트웨어는 변화에 유연하게 대응해야 하며, 비즈니스 요구 변화에 따라 지속적으로 진화해야 함.

### 4. **변경 대응 (Coping with Change)**
- 소프트웨어 프로젝트에서 변화는 필연적임. 
  - **변경 예측(Change Anticipation)**: 변경이 발생하기 전에 이를 예측하고 대비하는 활동.
  - **변경 허용(Change Tolerance)**: 변경이 발생했을 때 이를 수용할 수 있도록 프로세스를 설계.
- **시스템 프로토타이핑(System Prototyping)**: 고객 요구 사항을 확인하고 설계 결정을 검증하기 위해 시스템의 일부분을 빠르게 개발.
- **점진적 인도(Incremental Delivery)**: 시스템의 증분을 고객에게 제공하여 피드백을 받고, 이를 통해 변경을 최소화하고 수용함.

### 5. **프로세스 개선 (Process Improvement)**
- **프로세스 개선**: 기존 프로세스를 이해하고 이를 변화시켜 제품 품질을 높이고 비용을 절감하며 개발 시간을 단축.
- **프로세스 성숙도 모델(Capability Maturity Model, CMM)**:
  - **초기 단계(Initial)**: 통제가 이루어지지 않는 단계.
  - **반복 가능 단계(Repeatable)**: 제품 관리 절차가 정의되고 사용됨.
  - **정의 단계(Defined)**: 프로세스 관리 절차가 정의되고 사용됨.
  - **관리 단계(Managed)**: 품질 관리 전략이 정의되고 사용됨.
  - **최적화 단계(Optimizing)**: 프로세스 개선 전략이 정의되고 사용됨.

#### 개선 접근 방식
- **프로세스 성숙도 접근법**: 기술적 및 관리적 관행을 개선하고 성숙도를 높이는 방식.
- **애자일 접근법**: 반복적인 개발과 절차 간소화에 중점을 둠. 고객 요구에 빠르게 대응하고, 기능을 신속하게 전달하는 것이 핵심.


애자일 

### 1. **애자일 소프트웨어 개발의 배경**
- **신속한 소프트웨어 개발**이 중요한 요구사항이 됨. 기업은 빠르게 변화하는 환경 속에서 요구사항이 계속 변동되며, 이를 반영한 소프트웨어 개발이 필요.
- **계획 주도 개발(Plan-driven development)**은 일부 시스템에 필수적이나, 변화하는 비즈니스 요구사항에 대응하기 어려움.
- **애자일 개발 방법론**은 1990년대 후반에 등장해 소프트웨어 시스템의 배포 시간을 획기적으로 단축하는 것을 목표로 함.

### 2. **애자일 방법론**
- 애자일 방법론은 **코드** 중심으로 설계보다 빠른 소프트웨어 제공을 목표로 함.
- **특성**:
  - 문서를 최소화하고 작동하는 소프트웨어에 중점을 둠.
  - 반복적인 접근법으로 빠르게 변화하는 요구사항에 적응.
- **애자일 선언문(Agile Manifesto)**: 개인과 상호작용, 작동하는 소프트웨어, 고객 협업, 변화에 대한 응답을 강조함.

### 3. **애자일의 원칙**
- **점진적 인도**: 고객이 각 증분에 포함할 요구사항을 명시하고 소프트웨어는 단계적으로 개발됨.
- **고객 참여**: 고객은 개발 과정 내내 밀접하게 관여하며 새로운 요구사항을 제공하고 시스템을 평가함.
- **변화 수용**: 시스템 요구사항의 변화를 예상하고 그 변화를 수용할 수 있도록 설계.
- **단순성 유지**: 소프트웨어와 개발 과정에서 가능한 단순성을 유지.

### 4. **익스트림 프로그래밍(XP)**
- **XP 프로그래밍**은 반복적 개발에 극단적인 접근을 취함.
  - 하루에도 여러 번 새 버전을 빌드하고, 매 2주마다 새로운 기능을 제공.
  - 모든 테스트가 성공해야 빌드를 통과.
- **핵심 원칙**:
  - **소규모 릴리즈**: 비즈니스 가치를 제공하는 최소한의 기능을 먼저 개발.
  - **테스트 우선 개발(Test-First Development)**: 기능을 구현하기 전에 자동화된 테스트를 작성.
  - **리팩토링**: 코드를 지속적으로 개선하여 단순하고 유지보수가 용이하도록 만듦.
  - **짝 프로그래밍**: 두 명의 개발자가 함께 코드를 작성하여 코드 소유권을 공유하고 품질을 높임.
  - **연속적 통합**: 모든 작업이 완료되면 즉시 시스템에 통합하고 테스트를 진행.

### 5. **애자일 프로젝트 관리 (Scrum)**
- **Scrum**은 애자일 방법론 중 하나로 반복적 개발을 관리하는 데 중점을 둠.
  - **스프린트(Sprint)**: 2~4주 동안 소프트웨어 증분을 개발하는 반복 주기.
  - **Scrum 마스터**는 팀을 외부 방해로부터 보호하고 Scrum 과정이 잘 유지되도록 지원.
  - **제품 백로그(Product backlog)**: 해야 할 작업 목록으로, 사용자 스토리나 기능 정의가 포함됨.
  - **잠재적 전달 가능 제품 증분**: 스프린트 후 제공할 수 있는 상태의 소프트웨어.

### 6. **애자일 방법론의 확장**
- **소규모 프로젝트**에 적합하며, 대규모 프로젝트에서는 애자일 방법론의 기본 원칙을 유지하면서 조정이 필요.
- **대규모 시스템** 개발에서는 다수의 이해관계자와 긴 개발 시간이 필요하며, 규제 준수가 필수적일 때 계획 기반 접근 방식이 요구될 수 있음.

### 7. **애자일 테스트 개발**
- **테스트 주도 개발(Test-Driven Development)**: 기능을 구현하기 전에 테스트를 작성하고, 코드는 그 테스트를 통과해야 함.
- **자동화된 테스트**: 테스트를 자동화하여 새로운 기능이 추가될 때마다 기존 및 새 테스트를 실행하여 문제를 즉시 파악.

### 1. **DevOps 개요 (Overview of DevOps)**
#### DevOps가 필요한 이유
- **기존 개발 방식의 문제점**: 소프트웨어 개발 프로세스가 서로 단절된 상태에서 진행되며, 각 단계 간 상호작용이 부족함.
  - 개발 팀, IT 운영 팀, 전략 팀, 마케팅 팀 간의 의사소통 부재로 인해 프로젝트 진행 시 문제가 발생하고, 개발 지연이 자주 일어남.
  
#### DevOps 정의
- **DevOps는 소프트웨어 개발 방법론**으로, 개발(Dev), 운영(Ops), 사용자 피드백을 상호 연결하는 반복적인 메커니즘을 사용.
- **목표**: 개발 팀과 IT 운영 팀 간의 작업을 통합 및 자동화하여 시스템 개발 생명 주기를 단축하고, 높은 품질의 소프트웨어를 빠르게 제공.
- **Agile 및 Lean** 방법론을 기반으로 함.
- DevOps는 조직 내 **문화적 변화를 추구**하며, 개인의 작업에 대한 사고 방식을 바꾸고, 작업 간의 협업을 촉진함.

#### Lean 사고 (Lean Thinking)
- **Lean 소프트웨어 개발**: 초기 제조업에서 시작된 Lean 개발 방식은 이제 관리, UX, 스타트업, 소프트웨어 개발에 적용되고 있음.
- **원칙**:
  - 낭비를 제거하고 학습을 확대.
  - 가능한 늦게 결정하고, 가능한 빨리 배포.
  - 팀에 권한을 부여하고, 전체 최적화를 추구함.

### 2. **DevOps 원칙 (Principles of DevOps)**
- **자동화**:
  - 자동화는 개발자가 코드를 작성하고 새로운 기능을 개발하는 데 더 많은 시간을 할애할 수 있도록 도와줌.
  - CI/CD(지속적 통합/지속적 배포) 파이프라인에서 자동화는 인간의 실수를 줄이고 팀 생산성을 높임.
  
- **협업**:
  - DevOps의 핵심은 **협업**에 있음.
  - 개발 팀과 운영 팀이 하나의 기능적 팀으로 통합되어 전체 개발 및 배포 주기 동안 피드백을 공유하고 협업함.
  
- **지속적 개선**:
  - 짧은 반복 주기를 통해 고객 피드백에 빠르게 대응하고, 지속적으로 시스템 성능을 개선함.
  - 실시간 모니터링 및 신속한 배포를 통해 사용자 피드백을 수집하고, 이를 바탕으로 제품을 개선함.
  
- **고객 중심 행동**:
  - DevOps 팀은 짧은 피드백 루프를 통해 고객의 요구를 반영하고, 실시간 사용자 모니터링을 통해 문제를 해결함.
  
- **끝을 염두에 둔 개발(Create with End in Mind)**:
  - DevOps 팀은 제품의 전체 주기를 이해하고, 실질적인 문제를 해결하는 제품을 만들도록 노력해야 함.

### 3. **DevOps의 장점 (Benefits of DevOps)**
- **협업과 신뢰**: DevOps는 **공유 책임** 문화를 구축하며, 투명성을 높이고 빠른 피드백을 가능하게 함.
- **더 빠른 릴리스, 더 스마트한 업무**: DevOps를 실천하는 팀은 더 자주, 더 빠르게 릴리스를 진행하며, 품질도 높아짐.
  - 예: 2019년 DevOps 보고서에 따르면, 높은 성과를 내는 팀은 낮은 성과 팀보다 208배 더 자주 배포하고, 106배 더 빠르게 배포.
- **문제 해결 시간 단축**: DevOps 팀은 완전한 투명성과 원활한 커뮤니케이션을 통해 다운타임을 줄이고, 문제를 더 빠르게 해결할 수 있음.
- **계획되지 않은 업무의 더 나은 관리**: 자동화와 협업을 통해 복잡성을 줄이고, 발생하는 문제에 대해 더 신속하게 대응 가능.

### 4. **DevOps 프로세스 (DevOps Process)**
- **계획(Plan)**: 프로젝트의 작업을 계획하고, 일정 및 프로젝트 관리 도구를 설정함. Agile 방법론의 사용자 스토리 프로세스를 사용해 작업을 계획.
- **코딩(Code)**: 코드 개발 및 리뷰를 진행하며, 개발 팀과 운영 팀이 같은 코드 도구(GitHub, GitLab 등)를 공유함.
- **빌드(Build)**: 소스 코드를 컴파일, 테스트, 배포 가능한 형식으로 변환.
  - CI/CD 도구를 사용해 소스 코드 관리(SCM)에서 소스 코드를 확인하고 빌드.
- **테스트(Test/Verify)**: 자동화된 테스트를 통해 위험을 줄이고, 버그가 배포되지 않도록 보장.
- **릴리스(Release)**: 테스트를 통과한 코드가 배포될 준비가 완료됨.
- **배포(Deploy)**: 운영 팀이 새 기능을 프로덕션 환경에 배포하며, 자동화된 지속적 배포 설정도 가능.
- **운영(Operate)**: 인프라를 관리하고, 보안 문제 및 로그 관리를 담당함.
- **모니터링(Monitor)**: 실시간 모니터링을 통해 문제를 빠르게 해결하고 사용자 경험을 개선함.

### 5. **DevOps 실무 적용 (DevOps in Practice)**
#### DevOps 도구 체인 (DevOps Tool Chains)
- **DevOps 도구 체인**: 다양한 공급업체의 도구로 구성된 통합 유닛으로, 소프트웨어 설계, 빌드, 테스트, 관리, 측정, 운영을 지원.
- **핵심 요소**:
  - 지속적 통합, 지속적 배포, 자동화, 협업.

#### DevOps 성능 측정 (DevOps Performance Measurement)
- DevOps 성능을 측정하는 주요 지표:
  - **배포 주기(Deployment Frequency)**, **배포 크기(Deployment Size)**, **배포 시간(Deployment Time)**, **리드 타임(Lead Time)**, **결함 제거율(Defect Escape Rate)**, **가용성(Availability)** 등.

#### DevOps와 Agile 비교
- **Agile**: 개발자와 제품 관리 간의 협업을 강조, 소프트웨어 개발에서 코드 완료까지의 흐름을 중시.
- **DevOps**: 운영 팀을 포함하여, **배포와 유지보수**까지의 흐름을 확장.
  - 두 방법론 모두 소프트웨어 개발 속도와 품질을 개선하는 것을 목표로 하며, 상호 보완적임.

### 6. **결론**
- DevOps는 **개발(Dev)**과 **운영(Ops)** 간의 상호 작용을 통해 소프트웨어 개발의 속도와 품질을 개선하는 방법론임.
- DevOps 프로세스는 계획, 코딩, 빌드, 테스트, 릴리스, 배포, 운영, 모니터링의 단계를 포함함.
- Agile과 DevOps 모두 소프트웨어 개발 속도와 품질을 높이기 위한 방법론으로, DevOps는 Agile의 확장된 개념으로 볼 수 있음.



### **제3장 프로젝트 관리**

---

#### **3-1 소프트웨어 프로젝트 관리**

##### **1. 소프트웨어 프로젝트 관리란?**

- **정의**: 소프트웨어를 일정과 예산 내에서 조직의 요구사항에 맞게 제공하기 위한 활동.
- **필요성**: 소프트웨어 개발은 항상 예산과 일정의 제약을 받으며, 관리 없이는 목표 달성이 어려움.

##### **2. 소프트웨어 프로젝트 성공 기준**

- **정해진 시간 내에 소프트웨어를 제공**: 고객과 약속된 시간 준수.
- **예산 내에 비용 유지**: 전체 비용이 예산을 초과하지 않도록 관리.
- **고객의 기대 충족**: 고객의 요구사항과 기대에 부합하는 소프트웨어 제공.
- **팀의 일관성과 기능 유지**: 개발 팀의 협업과 효율성 유지.

##### **3. 소프트웨어 관리의 특징**

- **무형의 제품**: 소프트웨어는 보이지 않기 때문에 진행 상황을 시각적으로 확인하기 어려움.
- **일회성 프로젝트**: 대규모 소프트웨어 프로젝트는 이전과 다른 특성을 가지므로 경험 많은 관리자도 예측이 어려움.
- **가변적이고 조직 특화된 프로세스**: 소프트웨어 프로세스는 예측하기 어렵고 조직마다 다름.

##### **4. 프로젝트 관리에 영향을 미치는 요소**

- **회사 규모**
- **소프트웨어 고객**
- **소프트웨어 규모**
- **소프트웨어 유형**
- **조직 문화**
- **소프트웨어 개발 프로세스**

##### **5. 관리 활동**

- **프로젝트 계획 수립**: 일정 계획, 작업 할당.
- **위험 관리**: 잠재적 위험 식별, 모니터링 및 대처.
- **인력 관리**: 팀 구성원 선택, 효과적인 팀워크 구축.
- **보고**: 진행 상황을 고객과 조직의 관리자에게 보고.
- **제안서 작성**: 프로젝트의 목표와 수행 방법을 기술하여 계약을 따내기 위한 문서 작성.

---

#### **3-2 위험 관리**

##### **1. 위험 관리란?**

- **정의**: 프로젝트에 영향을 미칠 수 있는 위험을 식별하고 그 영향을 최소화하기 위한 계획 수립.
- **필요성**: 소프트웨어 개발은 불확실성이 내재되어 있으며, 이를 예측하고 대처해야 함.

##### **2. 위험 분류**

- **프로젝트 위험**: 일정이나 자원에 영향.
- **제품 위험**: 소프트웨어의 품질이나 성능에 영향.
- **비즈니스 위험**: 소프트웨어를 개발하거나 구매하는 조직에 영향.

##### **3. 위험 관리 프로세스**

1. **위험 식별**: 잠재적 위험 요소 식별.
2. **위험 분석**: 각 위험의 발생 확률과 영향을 평가.
3. **위험 계획 수립**: 위험을 회피하거나 최소화하기 위한 전략 수립.
4. **위험 모니터링**: 프로젝트 기간 동안 위험을 지속적으로 감시.

##### **4. 위험 식별 방법**

- **기술적 위험**
- **조직적 위험**
- **인적 위험**
- **요구사항 위험**
- **견적 위험**

##### **5. 위험 분석**

- **확률 평가**: 매우 낮음, 낮음, 중간, 높음, 매우 높음.
- **영향 평가**: 치명적, 심각, 허용 가능, 무시 가능.

##### **6. 위험 대응 전략**

- **회피 전략**: 위험 발생 확률을 낮춤.
- **최소화 전략**: 위험의 영향을 줄임.
- **대응 계획**: 위험이 현실화될 경우 대처 방안 마련.

##### **7. 위험 모니터링**

- 위험의 발생 가능성과 영향을 지속적으로 평가하고 관리 회의에서 논의.

---

#### **3-3 인력 관리**

##### **1. 인력 관리의 중요성**

- **핵심 자산**: 사람은 조직의 가장 중요한 자산.
- **관리자의 역할**: 사람 중심의 관리로 프로젝트 성공에 기여.
- **실패 요인**: 인력 관리의 실패는 프로젝트 실패로 이어질 수 있음.

##### **2. 동기 부여**

- **중요성**: 동기 부여된 인력은 효율성과 생산성이 높음.
- **방법**:
  - **기본적 필요**: 생리적, 안전적 필요 충족.
  - **개인적 필요**: 존중, 자아실현.
  - **사회적 필요**: 소속감, 팀워크.

##### **3. 매슬로우의 인간 욕구 이론**

- **욕구 단계**: 생리적 욕구 → 안전 욕구 → 사회적 욕구 → 존경 욕구 → 자아실현 욕구.
- **적용**: 소프트웨어 개발자는 상위 단계의 욕구 충족을 통해 동기 부여됨.

##### **4. 성격 유형과 동기 부여**

- **과업 지향형**: 일 자체에서 동기를 얻음.
- **자기 지향형**: 개인의 성공과 인정을 추구.
- **상호작용 지향형**: 동료와의 관계에서 동기를 얻음.
- **균형**: 효과적인 팀은 다양한 성격 유형의 조합이 필요.

---

#### **3-4 팀워크**

##### **1. 팀워크의 중요성**

- **협업 필요성**: 소프트웨어 개발은 팀 활동이며, 효과적인 협업이 중요.
- **팀의 응집력**: 팀원들이 팀을 개인보다 우선시할 때 높은 성과를 냄.

##### **2. 효과적인 팀의 특징**

- **공통의 목표**: 팀원들이 동일한 목표를 공유.
- **의사소통**: 원활한 정보 교환과 의견 공유.
- **상호 신뢰**: 팀원 간의 신뢰와 존중.

##### **3. 팀 구성**

- **팀원 선정**: 기술적 능력과 성격 유형을 고려하여 팀원 선정.
- **팀 구조**: 공식적 구조보다는 유연한 구조가 효과적.
- **의사소통 방식**: 공식적 회의뿐만 아니라 비공식적 소통도 중요.

##### **4. 그룹 조직화**

- **비공식 그룹**: 팀원들이 자율적으로 역할을 수행하고 결정에 참여.
- **리더의 역할**: 외부와의 인터페이스 역할, 팀 내 작업 할당은 팀원 간 협의로 결정.

---

#### **3-5 프로젝트 팀의 조직화**

##### **1. 직능별 조직 (Functional Organization)**

- **특징**: 부서별로 역할을 나누고, 프로젝트에 따라 협업.
- **장점**: 전문성 강화, 자원 관리 효율성.

##### **2. 프로젝트별 조직 (Project Organization)**

- **특징**: 프로젝트 중심으로 팀을 구성하고 운영.
- **장점**: 의사소통 경로 단축, 프로젝트 집중도 향상.

##### **3. 매트릭스 조직 (Matrix Organization)**

- **특징**: 직능별 조직과 프로젝트별 조직의 혼합 구조.
- **장점**: 유연한 자원 배치, 전문성 활용과 프로젝트 집중도 모두 달성.

##### **4. 애자일 조직 (Agile Organization)**

- **특징**: 작은 팀 단위로 유연하고 민첩하게 작업.
- **장점**: 빠른 의사 결정, 변화에 대한 빠른 대응, 팀원 간 긴밀한 협업.

---

#### **핵심 요점 정리**

- **프로젝트 관리의 중요성**: 소프트웨어 프로젝트의 시간과 예산 내 성공을 위해 필수.
- **위험 관리**: 잠재적 위험을 식별하고 대처 전략을 수립하여 프로젝트 실패를 예방.
- **인력 관리**: 동기 부여와 팀 구성으로 개인과 팀의 성과 극대화.
- **팀워크**: 효과적인 의사소통과 협업으로 프로젝트 목표 달성.
- **조직 구조**: 프로젝트 특성에 맞는 조직 구조를 선택하여 효율성 향상.


# **제2장 애자일 소프트웨어 개발**

## **2-1. 애자일 방법론의 배경**

### **1. 신속한 소프트웨어 개발**

- **현대의 요구사항**: 빠른 개발과 전달이 가장 중요한 요구사항이 됨.
  - 비즈니스 환경이 빠르게 변화하여 안정적인 소프트웨어 요구사항을 정의하기 어려움.
  - 소프트웨어는 비즈니스 니즈를 반영하여 빠르게 발전해야 함.

- **계획 중심 개발의 한계**:
  - 일부 시스템에는 필수적이지만 빠르게 변화하는 비즈니스 요구사항을 충족시키지 못함.

- **애자일 개발 방법의 등장**:
  - 1990년대 후반에 등장하여 작동 가능한 소프트웨어 시스템의 전달 시간을 획기적으로 단축하는 것을 목표로 함.

### **2. 애자일 개발**

- **특징**:
  - 프로그램 명세, 설계, 구현이 상호 연관되어 진행됨.
  - 시스템은 버전이나 증분의 시리즈로 개발되며, 이해관계자가 각 버전의 명세와 평가에 참여.
  - 새로운 버전을 자주 평가를 위해 전달.
  - 자동화된 테스트 도구 등 광범위한 도구 지원 사용.
  - 최소한의 문서화로 작업 코드에 집중.

### **3. 계획 중심 개발과 애자일 개발의 비교**

- **계획 중심 개발**:
  - 개발 단계가 분리되어 있으며, 각 단계의 산출물이 사전에 계획됨.
  - 반드시 폭포수 모델을 의미하지는 않으며, 계획 중심의 증분 개발도 가능.
  - 활동 내에서 반복이 발생.

- **애자일 개발**:
  - 명세, 설계, 구현, 테스트가 상호 연관되어 진행됨.
  - 개발 프로세스 중 협상을 통해 산출물이 결정됨.

## **2-2. 애자일 방법론**

### **1. 애자일 방법론이란?**

- **배경**:
  - 1980~1990년대의 소프트웨어 설계 방법론의 복잡성에 대한 불만으로 인해 등장.
  - 코드 자체에 집중하고 설계보다는 구현에 초점을 맞춤.
  - 반복적인 접근 방식을 기반으로 하며, 작동 가능한 소프트웨어를 빠르게 제공하고 이를 빠르게 발전시킴.
  - 문서화를 제한하여 프로세스의 오버헤드를 줄이고, 과도한 재작업 없이 변화하는 요구사항에 빠르게 대응.

### **2. 애자일 선언문 (Agile Manifesto)**

- **핵심 가치**:
  - **개인과 상호작용**을 프로세스와 도구보다 중시.
  - **작동하는 소프트웨어**를 포괄적인 문서보다 중시.
  - **고객과의 협력**을 계약 협상보다 중시.
  - **변화에 대응**하는 것을 계획을 따르는 것보다 중시.
  - 우측의 항목에도 가치가 있지만, 좌측의 항목을 더 가치 있게 여김.

### **3. 애자일 방법론의 원칙**

1. **고객 참여**:
   - 고객이 개발 프로세스 전반에 적극적으로 참여해야 함.
   - 새로운 시스템 요구사항을 제공하고 우선순위를 지정하며, 시스템 반복 버전을 평가하는 역할.

2. **점증적 인도**:
   - 소프트웨어는 증분으로 개발되며, 고객이 각 증분에 포함될 요구사항을 지정.
   - 최소한의 유용한 기능 집합을 먼저 개발하고, 이후 기능을 점진적으로 추가.

3. **변화 수용**:
   - 시스템 요구사항의 변화를 예상하고, 이러한 변화를 수용할 수 있도록 시스템 설계.

4. **단순성 유지**:
   - 개발되는 소프트웨어와 개발 프로세스 모두에서 단순성에 초점.
   - 가능한 한 복잡성을 제거하려고 적극적으로 노력.

5. **프로세스가 아닌 사람 중심**:
   - 개발 팀원의 역량을 인식하고 이를 최대한 활용.
   - 팀원들이 지시된 프로세스 없이도 자체적인 작업 방식을 개발하도록 권장.

### **4. 애자일 방법론의 적용 분야**

- **적합한 경우**:
  - **제품 개발**: 소프트웨어 회사가 판매를 위한 중소 규모의 제품을 개발하는 경우.
    - 대부분의 소프트웨어 제품과 앱은 이제 애자일 접근 방식을 사용하여 개발됨.
  - **조직 내 맞춤형 시스템 개발**:
    - 고객이 개발 프로세스에 적극적으로 참여할 의지와 능력이 있는 경우.
    - 소프트웨어에 영향을 미치는 외부 규칙과 규제가 적은 경우.

## **2-3. 애자일 개발 기술: 익스트림 프로그래밍 (XP)**

### **1. 익스트림 프로그래밍 (XP)**

- **정의**:
  - 1990년대 후반에 개발된 매우 영향력 있는 애자일 방법론으로, 다양한 애자일 개발 기술을 도입.
  - 반복 개발에 대한 '극단적인' 접근 방식을 취함.

- **특징**:
  - 하루에도 여러 번 새로운 버전이 빌드될 수 있음.
  - 2주마다 고객에게 시스템 증분을 전달.
  - 모든 테스트는 빌드마다 실행되어야 하며, 테스트가 성공적으로 실행될 때만 빌드가 승인됨.

### **2. 익스트림 프로그래밍의 주요 실천 방법**

1. **점진적인 계획 (Incremental Planning)**:
   - 요구사항은 사용자 스토리 카드에 기록되며, 시간과 우선순위에 따라 릴리즈에 포함될 스토리가 결정됨.
   - 개발자는 이러한 스토리를 개발 '작업'으로 분해.

2. **소규모 릴리즈 (Small Releases)**:
   - 비즈니스 가치를 제공하는 최소한의 유용한 기능 집합을 먼저 개발.
   - 릴리즈는 자주 이루어지며 첫 릴리즈에 기능을 점진적으로 추가.

3. **단순한 설계 (Simple Design)**:
   - 현재 요구사항을 충족하기 위한 최소한의 설계만 수행.

4. **테스트 우선 개발 (Test-first Development)**:
   - 새로운 기능을 구현하기 전에 해당 기능에 대한 테스트를 작성.
   - 자동화된 단위 테스트 프레임워크를 사용.

5. **리팩토링 (Refactoring)**:
   - 코드의 단순성과 유지보수성을 유지하기 위해 지속적으로 코드를 개선.
   - 개발자는 코드 개선이 필요하다고 판단되면 즉시 리팩토링 수행.

6. **짝 프로그래밍 (Pair Programming)**:
   - 개발자들이 짝을 이루어 코드를 함께 작성하며, 서로의 작업을 검토하고 지원.
   - 공동 소유권과 코드의 품질 향상을 도모.

7. **공동 소유권 (Collective Ownership)**:
   - 모든 개발자는 시스템의 모든 부분에 대해 책임을 지며, 누구나 코드를 변경할 수 있음.

8. **지속적인 통합 (Continuous Integration)**:
   - 작업이 완료되면 즉시 전체 시스템에 통합.
   - 통합 후 모든 단위 테스트가 통과해야 함.

9. **유지 가능한 속도 (Sustainable Pace)**:
   - 과도한 초과 근무를 지양하며, 이는 코드 품질과 생산성을 저하시킬 수 있음.

10. **고객의 참여 (On-site Customer)**:
    - 최종 사용자의 대표가 개발 팀에 상주하며, 시스템 요구사항을 팀에 제공하고 구현 과정에 참여.

### **3. 익스트림 프로그래밍과 애자일 원칙**

- **증분 개발 지원**: 작은 규모의 시스템 릴리즈를 통해.
- **고객 참여 강화**: 고객이 팀에 상주하며 적극적으로 참여.
- **사람 중심의 접근**: 짝 프로그래밍과 공동 소유권을 통해.
- **변화 수용**: 정기적인 시스템 릴리즈를 통해.
- **단순성 유지**: 지속적인 코드 리팩토링을 통해.

### **4. 익스트림 프로그래밍의 주요 실천 방법 상세 설명**

#### **사용자 스토리를 통한 요구사항 관리**

- **사용자 스토리**:
  - 고객 또는 사용자가 시스템에 원하는 기능을 간단한 스토리나 시나리오 형태로 표현.
  - 스토리는 카드에 작성되며, 개발 팀은 이를 구현 작업으로 분해.
  - 스토리는 일정과 비용 추정의 기반이 됨.
  - 고객은 우선순위와 일정 추정에 따라 다음 릴리즈에 포함될 스토리를 선택.

#### **리팩토링**

- **의미**:
  - 코드의 구조를 개선하여 유지보수성과 이해도를 높임.
  - 중복 코드 제거, 클래스 계층 구조 재조직화, 메서드와 속성의 명명 개선 등.

- **이점**:
  - 코드가 명확해져 문서화 필요성 감소.
  - 코드 개선을 통해 변경에 대한 대응이 용이해짐.

#### **테스트 개발**

- **테스트 우선 개발 (Test-first Development)**:
  - 기능 구현 전에 테스트 코드를 작성하여 요구사항을 명확히 함.
  - 테스트는 자동화되어 실행되며, 모든 테스트가 통과해야 빌드가 승인됨.

- **고객 참여**:
  - 고객은 테스트 케이스 작성에 참여하여 요구사항이 정확히 구현되도록 지원.

- **테스트 자동화**:
  - 테스트는 실행 가능한 컴포넌트로 작성되어 자동화 프레임워크(예: JUnit)를 통해 실행.

#### **짝 프로그래밍**

- **방법**:
  - 두 명의 개발자가 한 컴퓨터에서 함께 코드를 작성.
  - 서로의 코드를 검토하고 실시간으로 피드백 제공.

- **장점**:
  - 코드 품질 향상.
  - 지식 공유를 통해 팀 전체의 역량 향상.
  - 코드의 공동 소유권 강화.

## **2-4. 애자일 프로젝트 관리: 스크럼 (Scrum)**

### **1. 애자일 프로젝트 관리**

- **전통적 접근**:
  - 프로젝트 관리자는 프로젝트를 계획하고, 무엇을 언제 누가 개발할지 결정.

- **애자일 접근**:
  - 반복적인 개발과 애자일 방법론의 실천 방법에 맞게 조정된 다른 접근 방식 필요.

### **2. 스크럼**

- **정의**:
  - 반복적 개발을 관리하는 데 초점을 맞춘 애자일 방법론.

- **3단계**:
  1. **초기 단계**:
     - 프로젝트의 일반적인 목표 설정과 소프트웨어 아키텍처 설계.
  2. **스프린트 사이클**:
     - 각 사이클은 시스템의 증분을 개발.
     - 일반적으로 2~4주 동안 진행.
  3. **프로젝트 마무리 단계**:
     - 프로젝트를 마무리하고, 필요한 문서 작성 및 학습 내용 평가.

### **3. 스크럼의 주요 용어**

- **개발 팀 (Development Team)**:
  - 최대 7명의 자기 조직화된 개발자 그룹.
  - 소프트웨어와 기타 필수 프로젝트 문서 개발 책임.

- **스프린트 (Sprint)**:
  - 개발 반복 주기.
  - 각 스프린트는 작동 가능한 소프트웨어 증분을 생성.

- **스크럼 미팅 (Scrum Meeting)**:
  - 매일 진행되는 짧은 회의로, 팀의 진행 상황 검토 및 당일 작업 우선순위 지정.

- **스크럼 마스터 (Scrum Master)**:
  - 스크럼 프로세스가 잘 진행되도록 지원하고 팀을 외부 방해로부터 보호.
  - 프로젝트 관리자가 아닌 팀의 촉진자 역할.

- **제품 백로그 (Product Backlog)**:
  - 프로젝트에서 수행해야 할 작업 목록.
  - 기능 정의, 요구사항, 사용자 스토리 등을 포함.

- **제품 소유자 (Product Owner)**:
  - 제품 기능이나 요구사항을 식별하고 우선순위를 지정하며 백로그를 지속적으로 검토.

### **4. 스크럼 프로세스**

1. **계획 수립**:
   - 제품 백로그를 기반으로 스프린트에서 개발할 기능과 작업을 선택.
   - 개발 팀과 고객이 함께 참여.

2. **스프린트 실행**:
   - 팀은 자체적으로 조직하여 선택된 작업을 개발.
   - 스프린트 동안 팀은 외부로부터 격리되며 스크럼 마스터를 통해서만 소통.

3. **일일 스크럼 미팅**:
   - 모든 팀원이 참석하여 진행 상황 공유, 문제점 논의, 다음 날 계획 수립.

4. **스프린트 검토 및 회고**:
   - 스프린트 종료 시 작업 결과를 검토하고 이해관계자에게 시연.
   - 다음 스프린트를 위한 계획 수립.

### **5. 스크럼의 장점**

- **투명성 강화**:
  - 팀 전체가 모든 것을 볼 수 있어 의사소통이 향상.

- **신속한 문제 대응**:
  - 일일 미팅을 통해 문제를 빠르게 식별하고 해결.

- **고객 만족도 향상**:
  - 기능이 제때 전달되어 고객이 제품을 확인하고 피드백 제공.

- **팀 응집력 강화**:
  - 공동의 목표와 책임감을 통해 긍정적인 문화 조성.

## **2-5. 애자일 방법론의 규모 확장**

### **1. 애자일 방법론의 규모 확장**

- **도전 과제**:
  - 애자일 방법론은 소규모 공동 작업 팀에 가장 적합.
  - 대규모 프로젝트에서는 팀 간의 의사소통과 조정이 어려움.

- **확장 방법**:
  - **스케일 업 (Scaling Up)**: 대규모 시스템 개발에 애자일 방법론 적용.
  - **스케일 아웃 (Scaling Out)**: 대규모 조직 전체에 애자일 방법론 도입.

- **중요 요소**:
  - 유연한 계획, 빈번한 시스템 릴리즈, 지속적인 통합, 테스트 주도 개발, 효과적인 팀 의사소통 유지.

### **2. 애자일 방법론 적용 시 현실적인 문제**

- **계약상의 문제**:
  - 전통적인 소프트웨어 계약은 명세 기반으로 진행되므로 애자일의 유연한 명세 변경과 충돌.
  - 시간 기반의 계약이 필요하지만, 이는 법무팀에서 리스크로 인식.

- **소프트웨어 유지보수**:
  - 애자일은 새로운 소프트웨어 개발에 적합하지만, 유지보수에는 한계가 있을 수 있음.
  - 유지보수를 위해서는 문서화와 원래 개발 팀의 지속적인 참여가 필요.

- **분산 팀**:
  - 애자일은 동일 장소에서 작업하는 소규모 팀에 적합하지만, 글로벌 분산 팀에는 적용이 어려움.

### **3. 애자일과 계획 중심 방법론의 조화**

- 대부분의 프로젝트는 애자일과 계획 중심 방법론의 요소를 모두 포함.
- 프로젝트의 특성에 따라 균형을 조정해야 함.

### **4. 대규모 시스템 개발에서의 애자일 적용**

- **시스템 이슈**:
  - 대규모 시스템은 외부 규제와 제한을 받을 수 있음.
  - 장기간의 개발 기간으로 인해 팀 구성원의 교체 가능성 높음.
  - 다양한 이해관계자의 참여로 인해 모든 요구사항을 반영하기 어려움.

- **팀 이슈**:
  - 팀원의 역량과 조직 방식이 중요.
  - 분산된 팀의 경우 설계 문서화가 필요할 수 있음.

- **조직적 이슈**:
  - 조직의 문화와 관행이 애자일의 비형식성과 충돌할 수 있음.
  - 고객의 적극적인 참여가 어려울 수 있음.

## **핵심 요점 정리**

1. **애자일 개발은 반복적 개발 방법으로, 빠른 소프트웨어 개발과 빈번한 릴리즈, 프로세스 오버헤드 감소, 높은 코드 품질에 초점을 맞춤.**

2. **애자일 개발의 실천 방법에는 사용자 스토리를 통한 시스템 명세, 지속적인 소프트웨어 개선, 테스트 우선 개발, 고객의 적극적인 참여 등이 포함됨.**

3. **스크럼은 반복 주기(스프린트)를 중심으로 한 프로젝트 관리 프레임워크로, 스프린트마다 작동 가능한 시스템 증분을 개발.**

4. **실제 개발 방법은 계획 중심과 애자일 개발의 혼합인 경우가 많으며, 프로젝트의 특성에 따라 균형을 맞춰야 함.**

5. **대규모 시스템에 애자일 방법론을 적용하는 것은 어려움이 있으며, 사전 설계와 문서화가 필요하고 조직의 관행과 애자일 접근 방식이 충돌할 수 있음.**
