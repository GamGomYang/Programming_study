union, union all

union all - 중복을 확인하지 않음
union - 중복 제거 작업을 위해서 소트연산 시행

서로 포함되어지지 않는 독립적인 관계에서는 중복성 체크가 필요가 없다.
하지만 union연산을 수행하면 불필요한 소트 연산이 사용되어진다.
그러므로 서로 상호 배타적인 인스턴스라면 union all을 사용하는것이 성능 측면에서 좋다.

select 결제번호, 결제수단코드, 주문번호, 결제금액, 결제일자, 주문일자 …
from 결 제
where 결제일자 = '20180316'
UNION
select 결제번호, 결제수단코드, 주문번호, 결제금액, 결제일자, 주문일자 …
from 결 제
where 주문일자 = '20180316'

이렇게 union 연산을 하면 
결재일자와 주문일자가 동일한 인스턴스들은 중복되어져서 나타난다.
그래서 union 연산을 통해서 인스턴스의 중복을 제거 하려고 했으나.
소트연산으로 인해서 비용이 커졌다.

어떻게 하면 소트연산을 줄이며 할 수 있을까?

select 결제번호, 결제수단코드, 주문번호, 결제금액, 결제일자, 주문일자 …
from 결제
where 결제일자 = '20180316'
UNION ALL
select 결제번호, 결제수단코드, 주문번호, 결제금액, 결제일자, 주문일자 …
from 결제
where 주문일자 = '20180316'
and 결제일자 <>'20180316'

이렇게 <>를 추가해서 결재일자가 동일한 인스턴스를 제거하면된다.

하지만 <> 은 NULL 조차 제거해버리는 단점이 있는데
이때 LNNVL함수를 사용하여 NULL 제거를 방지 할 수 있다.

<> : 해당 조건 제거
LNNVL : 해당조건 제거 + NULL 제거 방지


-distinct, minus 보단 exist not exist 사용하기

distinct는 중복된 인스턴스를 제거하는 연산을 하는데
모든 데이터를 가져와서 중복 제거 수행 -> 속도가 굉장히 느리다.

exists를 사용하면 데이터가 존제하는 순간 연산이 종료되어지기 때문에 훨신더 빨라진다.

SELECT DISTINCT p.상품번호, p.상품명, p.상품가격
FROM 상품 p, 계약 c
WHERE p.상품유형코드 = :pclscd
AND c.상품번호 = p.상품번호
AND c.계약일자 BETWEEN :dt1 AND :dt2
AND c.계약구분코드 = :ctpcd;

이러한 쿼리가 있다고 하면 
만약 계약이 100개가 있다고 하면 동일한 상품번호를 가진 계약 100개를 전부 탐색하기 때문에
성능 측면에서 굉장히 느려진다.

exists를 이용하면 해당 인스턴스 하나를 발견하면 바로 종료하기때문에 훨씬 빨라진다.

쿼리를 고쳐보면

SELECT p.상품번호, p.상품명, p.상품가격
FROM 상품 p
WHERE p.상품유형코드 = :pclscd
AND EXISTS (
    SELECT 1  (1개가 아니라 데이터의 존재유무 판단을 위해 1 사용 (있으면 TRUE 없으면 FALSE 반환))
    FROM 계약 c
    WHERE c.상품번호 = p.상품번호
    AND c.계약일자 BETWEEN :dt1 AND :dt2
    AND c.계약구분코드 = : ctpcd
);

이렇게 exists 서브쿼리를 이용하면 해당 조건 하나를 찾으면 바로 종료한다.

-조인 방식 변경으로 소트연산 줄이기

지점 ID + 계약일시로 이루어진 인덱스를 이용해서
해당 쿼리를 실행하면 해시 조인으로 인해서 불필요한 소트과정이 생성되어진다.

select c.계약번호, c.상품코드, p.상품명, p.상품구분코드, c.계약일시, c.계약금액

해시조인은 빠른 조인 작업을 수행함으로써 대량의 데이터 조인시 적합한 조인이지만
해시조인은 정렬을 보장하지 않기 떄문에 별도 정렬(소트작업)이 필요하다.

NL 조인을 사용하면 인덱스를 활용하여 정렬된 데이터를 가져올 수 있으므로 소트 연산을 생략할 수 있다.
SELECT /*+ LEADING(c) USE_NL(p) */
c.계약번호, c.상품코드, p.상품명, p.상품구분코드, c.계약일시, c.계약금액
FROM 계약 c, 상품 p
WHERE c.지점ID = :brch_id
AND p.상품코드 = c.상품코드
ORDER BY c.계약일시 DESC;

NL조인을 사용하면 인덱스에서 이미 정렬된 데이터를 가져올 수 있기 때문에
소트 연산이 필요하지 않다.

`Sort Merge Join`은 조인 키 기준으로 정렬된 데이터라면 정렬 연산을 생략할 수 있지만, 정렬되지 않은 경우 `SORT` 연산이 발생할 수도 있다.
SELECT /*+ USE_MERGE(c p) */
c.계약번호, c.상품코드, p.상품명, p.상품구분코드, c.계약일시, c.계약금액
FROM 계약 c, 상품 p
WHERE c.지점ID = :brch_id
AND p.상품코드 = c.상품코드
ORDER BY c.계약일시 DESC;

소트 머지 조인 또한 인덱스에서 정렬된 데이터를 가져오기때문에 소트연산 불필요

6.2 Direct Path I/O

소량의 데이터는 버퍼캐시를 이용하면 빠르게 검색이 가능하지만
대량의 데이터는 오히려 버퍼캐시를 이용하면 검색속도가 더 느려진다.

direct path를 이용하면 버퍼캐시를 이용하지 않고 바로 데이터를 읽으므로 대용량 데이터에서는 속도가 더빠를 수 있다.

6.3.1 테이블 파티션

파티셔닝의 종류
1. range 파티션
2. list 파티션
3. hash 파티션

-range 파티션
시계열과 같은 특정 범위를 기준으로 데이터를 파티셔닝
-list 파티션
특정 리스트 값을 기준으로 데이터 파티셔닝 (지역별 , 카테고리)
사용자가 정의한 논리적인 그룹에 따라 오라클이 분할한다.

-hash 파티션
특정 해시 함수를 기반으로 데이터 분할 (고객 ID)
고객 id와 같은 변별력이 좋고 데이터가 고른 컬럼 파티션을 기준으로 선정
오라클이 정한 해시 알고리즘에 따라 임의로 분할

6.3.2 인덱스 파티션

파티션 인덱스의 종류 - 1. 로컬 파티션 인덱스 2. 글로벌 파티션 인덱스 3. 비 파티션 인덱스

1. 로컬 파티션 인덱스
테이블 파티션과 정확하게 1:1로 매칭되는 인덱스
오라클이 자동으로 관리하므로 테이블이 변경될때 수동 변경 필요 없음

2. 글로벌 파티션 인덱스
사용자가 테이블 파티션과 관계없이 독립적으로 인덱스를 구성 할 수 있다.
테이블 파티션이 변경되어지더라도 인덱스는 영향을 받지 않는다.
검색 성능을 최적화 하기 위해 특정 컬럼 기준으로 인덱스 별도 구성 가능

3. 비 파티션 인덱스
우리가 흔히 아는 일반적인 인텍스
테이블 전체를 하나의 인덱스로 관리
소규모 데이터는 적절하지만 대량데이터에서는 부담이 커질 수 있음


** 중요한 인덱스 파티션 제약 **
유니크 인덱스를 파티셔닝 하려면 파티션 키가 모두 인덱스 구성 컬럼이어야 한다.

-> primary key를 파티셔닝 하려면 파티션 키를 반드시 포함해야한다.
unique 인덱스를 파티셔닝 하려면 파티션 키가 반드시 인덱스 컬럼에 있어야한다.
즉 유니크 인덱스를 로컬 파티션으로 유지하려면 파티션 키를 포함
