인덱스 튜닝 - 테이블 액세스 최소화

- 인덱스 ROWID는 우편주소
ROWID는 우편주소 , 메인메모리 DB가 사용하는 포인터는 전화번호

ROWID는 결국 해싱과 래치 과정을 거치며 많은 과정을 거치기 때문에
고비용 작업이다.

- 인덱스 클러스터링 팩터(CF)
같은 군집끼리 모여있으면 좋은 클러스터링 팩터라고 생각하면 된다.

왜? 클러스터링 팩터가 좋은 컬럼은 검색 효율이 좋을까?
buffer pinning : 래치 획득과 해시체인을 거친 포인터를 해제하지 않고 유지하는 과정
버퍼 피닝을 통해서 테이블 액세스 횟수에 비해 블록 IO가 적게 발생한다.

- 인덱스 손익 분기점
table access by index scan > full table scan
인덱스 스캔이 테이블 풀 스캔 소요시간이 똑같은 지점
table access by index scan: 랜덤 액세스 , single block IO
full table scan : 시퀀셜 액세스 , mulitblock IO

클러스터링 팩터(CF)가 좋을 수록 손익분기점이 올라갈 수 있다.


- 온라인 프로그램 튜닝 vs 배치 프로그램 튜닝
온라인 프로그램 : 수백만 건 중 수십건만 일단 먼저 들고 오면 됨 (소량 데이터 갱신)
대부분 NL(nest loop) 조인을 사용

배치 프로그램 : 대량 데이터 읽고 갱신, 전체 범위 처리기준으로 튜닝
full scan , 해시조인 유리

- 인덱스 구조 테이블 (IOT : Index Organized Table)
테이블 데이터를 인덱스처럼 정렬해서 저장하는 구조
테이블을 따로 읽을 필요없이 바로 데이터를 읽을 수 있다.

효과
1. 테이블 액세스를 줄일 수 있음
2. 정렬상태로 저장되어지므로 범위(BETWEEN <= >=)검색에 유리

예제 - 영업실적 테이블
문제점 : 일자별로 기록되어져서 사번기준으로 정렬 안되어져 있음
사번으로 검색을 하면? -> 랜덤블록 365번 해야함 (CF가 나쁘다)

solution - IOT를 이용하여 해결
CREATE TABLE 영업실적 (
  사번 VARCHAR2(5),
  일자 VARCHAR2(8),
  ...
  CONSTRAINT 영업실적_pk PRIMARY KEY (사번, 일자)
) ORGANIZATION INDEX;

사번 기준으로 정렬된 구조 - 사원에 따라 데이터가 모여있음(CF좋음) - 랜덤 IO없이 조회

단점 : ROWID연산 불가(ROWID가 없음), 정렬유지 때문에 DML이 느림


- 클러스터 테이블
클러스터 테이블에는 인덱스 클러스터 , 해시 클러스터 두가지가 있다.

인덱스 클러스터 테이블
클러스터키 값이 같은 레코드들을 한블록에 모아서 저장하는 구조

인덱스 클러스터 테이블 구성방법
1. 클러스터 생성
create cluster c_dept# (deptno number(2)) index;

2. 클러스터 인덱스 정의
create index c_dept# on cluster c_dept#;

3. 클러스터 테이블 생성
create table dept(
    deptno number(2) not null,
    deptno varchar2(14) not null,
    loc varchar2(13))
    cluster c_dept#(deptno);

다른 레코드들과 달리 인덱스 클러스터는 테이블 레코드와 1:M의 관계를 갖는다.


- 해시 클러스터 테이블
인덱스를 사용하지 않고 해시 알고리즘을 사용해 클러스터를 찾아간다.

해시 클러스터 테이블 구성 방법 
1. 클러스터 생성
create cluster c_dept# (deptno number(2)) hashkeys4;

2. 클러스터 테이블 생성
create table dept(
    deptno number(2) not null,
    dname varchar2(14) not null,
    loc varchar2(13))
    cluster c_dept# (deptno);
