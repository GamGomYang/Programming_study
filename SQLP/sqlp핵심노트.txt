1. instance = SGA + 프로세스 집합
SGA (system global area) - db에서 공유되는 메모리 영역 (버퍼캐시, 로그버퍼(redo), system pool etc..)
PGA와 상반되어지는 개념이다.
SGA = 공유 메모리 PGA = 개별 프로세스 전용 메모리


2. 오라클 백그라운드 프로세스
system moniter (smon) : 시스템 재가동시 인스턴스 복구 및 임시 세그먼트 모니터링 및 정리
process moniter (pmon) : 이상이 생긴 프로세스가 사용하던 리소스 복구

data writers (dbwn) : 버퍼 캐시에 있는 dirty버퍼를 데이터 파일에 기록
   - dirty buffer -> 변경되었지만 아직 데이터 파일에 기록이 안된 데이터

log writer (lgwr) : 로그 버퍼 엔트리를 redo 로그에 기록
   - redo log -> 데이터 변경사항을 기록. 장애 발생시 복구하는데 사용
   - WAL (write ahead loggin) -> 데이터 변경 전 반드시 로그를 먼저 기록하는 방식

archiver (arcn) : 꽉찬 redo 로그가 덮어쓰여지기 전 archive 로그 디렉토리 백업
checkpoint (ckpt) : 이전 checkpoint가 일어나던 마지막 시점 이후의 데이터 베이스 변경사항을 db파일에 기록하도록 트리거링
체크포인트 정보 관리
recover (reco) : 분산 트랜잭션 과정에 발생한 문제를 해결
 
**로그버퍼에 로그는 DML을 수행하는 각 사용자 프로세스가 기록한다.
-> DML 사용자가 로그버퍼에 로그 기록 -> LGWR이 redo 로그 파일에 기록


3 & 4. 데이터 저장구조
블록 (block = page)
데이터 베이스에서 가장 작은 데이터 저장단위
디스크 입출력시 블록 단위로 이루어짐 -> 한 행을 검색해도 블록단위로 불러옴
블록이 가득 차면 새로운 블록에 저장
  - 책 한페이지와 유사 

익스텐드 (extent)
여러개의 블록들이 모인 저장 단위
특정 테이블이나 인덱스가 할당된 블록이 부족하면 익스텐트 단위로 블록 할당
한 익스텐트 내에서는 블록이 논리적 연속적 but 물리적으로는 아닐 수 있다.
  - 책의 한 챕터와 유사

세그먼트 (segment)
여러개의 익스텐트로 구성된 데이터 저장 단위
테이블, 인덱스 , 파티션, 클러스터 등 데이터를 저장하는 객체가 하나의 세그먼트
  - 한권의 책과 유사

테이블 스페이스 (table space)
테이블 스페이스는 여러개의 세그먼트를 포함하는 논리적 저장단위
여러 개의 데이터 파일로 구성
  - 도서관과 유사


5. 오라클이 undo를 수행하는 목적

 redo <-> undo

 Undo 수행 목적 
 1. Transcation Rollback
 2. Transcation Recovery
 3. Read Consistency
    - 다중 사용자가 공유자원 접근 시 한 사용자가 변경할때 다른사용자에게는 변경 전 데이터를 제공
    - 즉 데이터의 원래 상태를 볼 수 있도록 일관성을 보장해 주어야한다.

 Redo 수행 목적
 1. database recovery
    - db가 비정상 종료 시 데이터 복구 위해 사용
 2. transcation 보장 (commit이후 복구 가능)
    - commit 이후에도 redo로그를 통해 복구 할 수 있도록 보장함
 3. cache recovery


6. redo 로그 설명
 redo로그 - 데이터 베이스 변경사항을 기록하는 파일. 데이터 복구 가능
 1. database recovery ( = media recovery)
    - 디스크가 손상되거나 데이터가 사라졌을떄 , archived redo 로그를 이용해 복구
    - 만약 디스크가 고장났다면 redo로그를 아카이빙 해둔 파일이 있다면 db복구 가능
    - 이렇게 아카이빙 redo 로그를 이용하는것을 media recovery라고 한다.

 2. cache recovery ( = instance recovery)
    - 데이터가 메모리에만 저장된 상태에서 db가 꺼져도 redo를 통해 복구
    - db 속도를 높이기 위해 버퍼캐시에 먼저 저장하지만 휘발성 메모리로 사라질 위험이 있음
    - redo 로그가 있으면 이를 이용해 db복구 가능 (instance recovery)

 3. fast commit 
    - redo 로그 덕분에 빠르게 트랜잭션을 완료할 수 있음.
    - redo로그는 순차적 (append방식) 으로 기록됨으로 랜덤액세스보다 빠름
    - redo로 빠르게 기록하고 나중에 db에 반영한다. (= fast commit)

 추가 내용 : redo 로그 스위칭 & DB Hang 
    - 트랜잭션이 몰리면 redo로그가 자주 변경됨 (로그 스위칭)
    -> 백업(아카이빙) 작업도중 로그 스위칭이 발생되면 db가 멈추는 (DB Hang)이 발생함
    - 적절한 크기의 redo파일 설정 하여 db hang을 방지해야함

7. redo 메커니즘
 1. log force at commit 
    - 사용자가 트랜잭션을 커밋하면 최소한 로그는 데이터 파일에 안전하게 기록해야한다.
    - DML이 로그를 로그 버퍼에 저장 -> LGWR프로세스가 주기적으로 redo로그파일에 저장
    - 로그버퍼는 메모리이기 때문에 휘발성 위험이 있음
    -> 커밋시 반드시 로그 버퍼내용을 디스크에 저장한다.
    -> 커밋 시점에 반드시 redo로그 파일에 저장.
 
 2. Fast Commit
    - 사용자 요구 변경사항이 db에 저장이 안되어도 redo로그를 믿고 빠르게 커밋
    - 이후 DBWR프로세스가 변경된 데이터를 나중에 DB에 반영함.
 
 3. wirte ahead logging(WAL)
    - 데이터 블록을 변경전에 반드시 redo 로그를 먼저 기록해야한다.
    - 트랜잭션이 DML을 실행
    - 버퍼캐시에 데이터 반영 -> DBWR프로세스가 일정시간마다 dirty 블록을 디스크에 저장
    - **dirty 블록이 데이터 파일에 기록전에 redo 로그는 반드시 먼저 저장되어야함
    -> 그렇게 해야지만 redo 로그를 이용해 데이터 복구 가능

 추가 내용 : snapshot too old error (undo 관련)
    - 과거 데이터를 조회할때 undo 블록이 다른 트랜잭션에 의해 덮어쓰여서 조회를 못하는 상태
    - undo를 이용해 데이터를 복원하려고 할때 undo블록이 다른 트랜잭션에 덮어쓰여서 없어짐
    - undo정보를 찾을 수 없음 -> snapshot too old 오류 발생

 10. 버퍼 블록의 상태
  1. Free 버퍼 : 인스턴스 기동 후 아직 데이터가 얽히지 않아 비어있는상태
  2. dirty 버퍼 : 버퍼캐시에 적재된 이후 변경이 발생했지만 아직 데이터 파일에 기록하지 않아 동기화가 필요한 버퍼 블록
  3. pinned 버퍼 : 읽기 또는 쓰기 작업을 위해 현재 액세스 되고 있는 버퍼 블록
